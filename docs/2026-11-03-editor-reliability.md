# 编辑响应与保存回执改进

## 观察到的问题

2026-11-03 的实际界面操作多次在编辑弹窗出现后失去控制响应；同期通过 MCP 查询密钥元数据仍成功，待修正条目的修订版本没有变化。
Codex 宿主日志出现 `No ChatGPT browser route is available` 与 `mcp_app_sandbox.session_suspended`（`offscreen_timeout`）。
这些记录表明宿主路由/页面生命周期发生异常，但不能证明 AKSK Manager 导致了该异常，也不能证明插件进程崩溃。
日志原文与凭据值不纳入仓库。

源码中确认的可改进点：

- “编辑”额外请求 `get_secret_metadata`，在已有完整元数据与修订号时仍等待宿主返回；没有请求中的反馈。
- 工具请求使用 SDK 默认超时，传输失败直接暴露原始异常，缺少保存结果未知的状态。
- 刷新失败会清空已读取的列表，容易被误认为数据丢失。
- 保存回执丢失时无法区分“未保存”与“已保存但未收到响应”，重复提交可能导致重复新建。

## 修改

- 编辑使用当前列表记录立即打开，原生层保存时的修订号冲突检查保持不变。
- 初始化与工具调用明确限制为 15 秒；传输异常使用固定安全提示，不输出请求参数或原始异常。
- 未确认写入不自动重试，编辑器禁止再次提交，并暂停其他写入入口；用户可关闭弹窗，通过刷新核对记录。
- 刷新失败保留元数据快照，同时标记连接未确认并暂停写入；成功刷新后恢复。
- 同一表单提交加同步保护，防止连续事件重复调用保存。

## 验证与边界

使用合成数据模拟元数据请求无响应、已保存但回执丢失、刷新回执丢失及恢复；检查 ID 保持、无重复提交、版本冲突保护和无模型上下文泄漏。
模拟宿主测试不能证明 Codex 的后台挂起故障已解决；真实宿主的新版面板仍需持续验证。
不改动钥匙串服务名、访问组、签名团队、存储格式或实际凭据。
