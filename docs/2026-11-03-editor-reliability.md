# 编辑响应与保存回执改进

## 观察到的问题

2026-11-03 的实际界面操作多次在编辑弹窗出现后失去控制响应；同期通过 MCP 查询密钥元数据仍成功，待修正条目的修订版本没有变化。
Codex 宿主日志出现 `No ChatGPT browser route is available` 与 `mcp_app_sandbox.session_suspended`（`offscreen_timeout`）。
这些记录来自不同控制后端与面板实例，不能直接串成因果关系，也不能证明插件进程崩溃。下文的进一步诊断修正了最初的挂起归因。
日志原文与凭据值不纳入仓库。

源码中确认的可改进点：

- “编辑”额外请求 `get_secret_metadata`，在已有完整元数据与修订号时仍等待宿主返回；没有请求中的反馈。
- 工具请求使用 SDK 默认超时，传输失败直接暴露原始异常，缺少保存结果未知的状态。
- 刷新失败会清空已读取的列表，容易被误认为数据丢失。
- 保存回执丢失时无法区分“未保存”与“已保存但未收到响应”，重复提交可能导致重复新建。

## 修改

- 编辑使用当前列表记录立即打开，原生层保存时的修订号冲突检查保持不变。
- 初始化与工具调用明确限制为 15 秒；传输异常使用固定安全提示，不输出请求参数或原始异常。
- 未确认写入不自动重试，编辑器禁止再次提交，并暂停其他写入入口；用户可关闭弹窗，通过刷新核对记录。
- 刷新失败保留元数据快照，同时标记连接未确认并暂停写入；成功刷新后恢复。
- 同一表单提交加同步保护，防止连续事件重复调用保存。

## 验证与边界

使用合成数据模拟元数据请求无响应、已保存但回执丢失、刷新回执丢失及恢复；检查 ID 保持、无重复提交、版本冲突保护和无模型上下文泄漏。
模拟宿主测试不能证明 Codex 的后台挂起故障已解决；真实宿主的新版面板仍需持续验证。
不改动钥匙串服务名、访问组、签名团队、存储格式或实际凭据。

- 签名原生组件未修改，复用已有构建。安装前后 stdio 启动、13 个工具、内嵌界面资源和钥匙串读取检查通过。
- 已安装 `0.1.0+local.2f45841fd750`；安装与自动化测试不修改真实凭据。

## 进一步诊断：分开挂起与自动化超时

检查本机宿主 26.1027.61615 的已安装代码和当天按实例关联的日志，确认：

- 宿主仅对聊天滚动布局中的 `inline` 实例启用离屏挂起，且要求没有独立面板标签；离屏阈值为 300000 毫秒（5 分钟）。回到可见区域或离开该布局会取消挂起条件。这是宿主的资源回收策略，不是凭据后端崩溃。
- 早期 `offscreen_timeout` 日志主要属于旧的聊天卡片实例。重启后在北京时间 20:26 的自动化超时窗口，没有相应实例的挂起事件。
- `No ChatGPT browser route is available` 来自 IAB 浏览器发现后端，不能直接作为 MCP Apps 面板断联的证据。
- 对先前超时的同一个面板重新读取状态成功，不重开即可刷新到最新列表；连续五轮打开、取消编辑均成功（每轮约 0.10–0.16 秒），没有写入或显示凭据。
- 因而，旧聊天卡片的离屏挂起原因已确认，但那次 30 秒自动化调用超时的直接触发点未复现，不能声称两者是同一个故障。

## 显示模式修复

资源 `availableDisplayModes` 从 `[fullscreen, inline]` 收敛到 `[fullscreen]`，
初始化 `appCapabilities.availableDisplayModes` 同时显式声明 `[fullscreen]`。
这样宿主不会将凭据编辑器降为受离屏回收策略影响的聊天卡片；保持已有的独立面板布局。
此声明符合 [MCP Extensions 显示模式契约](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md#display-modes)。

回归测试分别检查资源响应和真实前端初始化消息，防止两个阶段再次不一致。
不修改宿主安装包、不关闭资源回收、不增加后台心跳，也不将敏感草稿持久化。
宿主版本可能改变策略；契约测试和模拟宿主测试不能替代真实宿主验收，也不能证明任意自动化超时已根治。

- 已在技能中记录恢复顺序：先读取原实例、核对写入结果，再决定恢复动作；不能把控制工具超时直接当作要求用户重开面板的理由。
- Postman CLI 在本机不提供 `status` 子命令。本次为本地 stdio 与 postMessage 契约，没有 HTTP 服务；使用项目原有测试和 stdio 客户端验证，没有建立或上传 Postman 工作区。

## Agent 修改入口及版本隔离补充

后续实现 update_secret 时，正式入口暴露了另一个可复现的问题：所有版本共用固定 Python 环境，且默认 wheel 缓存不跟踪源码/HTML，导致源码测试通过而正式启动仍发现旧工具列表。现已按插件路径隔离环境并增加源码/HTML 缓存键；最终安装版为 0.1.0+local.1a7c1a289838，实际入口核验通过。该发现不能反推先前 30 秒自动化超时也是由缓存造成。

既有记录的 agent 修改不再依赖面板控制；协议、边界及验证见 [Agent 修改契约](agent-editing.md)。
